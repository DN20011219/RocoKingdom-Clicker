# 更新日志 — 2026-09-30

一处行为修正：第四栏三个区域捕获按钮与 `F6` 热键统一走同一条带互斥检查的路径。

## 问题

「区域捕获」那一行有三个按钮，但只有两条路径：

| 按钮 | 原调用链 |
| --- | --- |
| 📐 拖拽圈选 | 按钮 → `_start_region_capture("drag")`（主线程直连） |
| 🪟 拾取窗口 | 按钮 → `_start_region_capture("window")`（主线程直连） |
| 🎙 录制区域 | 按钮 → `request_region_capture("drag")` → 队列 → 主线程排空 → `_start_region_capture` |
| `F6` 热键 | 钩子线程 → 互斥检查 → `request_region_capture("drag")` → 队列 → 同上 |

互斥检查（录制中 / 脚本运行中 / 回放中拒绝圈选）只写在 `_dispatch_hotkey()` 的热键分支里。因此**按 `F6` 会被拦下，点「📐 拖拽圈选」或「🪟 拾取窗口」却能直接把覆盖整个虚拟屏的 Tk 窗口弹到游戏上**。

绕队列本身是必要的：热键回调发生在低级键盘钩子线程，而 Tk 窗口不能在子线程创建，所以钩子线程只能投递请求、由主线程 `_drain_region_requests()` 排空后创建。「🎙 录制区域」按钮当初就是为了和热键行为一致才故意走队列的——只是另外两个按钮没有跟上。

## 修改

- **`Clicker.py`**：新增 `_region_capture_blocker()`，返回阻止圈选的原因（`None` 表示放行）；`request_region_capture()` 内部先过这道检查，被拦下时 toast 原因并返回 `False`，成功投递返回 `True`。`_dispatch_hotkey()` 的 `record_region` 分支删掉重复检查，直接调用。
  - 检查项在原有「录制中 / 脚本运行中 / 回放中」之外补上 **MIDI 演奏中（含倒计时）**——演奏时弹出全屏覆盖层同样会毁掉演奏，而 `start_region_click()` 早已有这条守卫，捕获入口却漏了。
- **`gui.py`**：`Api.request_region_capture()` 如实回传后端的布尔结果，不再无条件 `return True`。
- **`webview.py`**：`_on_record_region_request()` 改名并泛化为 `_on_region_capture_request(mode)`，三个按钮全部改为调用它；`_start_region_capture()` 降为纯执行层，docstring 写明「只应由 `_drain_region_requests` 调用」。`_rc_selector.busy` 检查保留在执行层（选择器实例在 GUI 侧，后端看不到）。
- **`tests/test_gui_smoke.py`**：新增 `RegionCaptureRoutingTest`（3 例）。把 `_start_region_capture` 换成记录桩后逐个 `invoke()` 三个按钮，断言每个都以正确的 mode 投递到后端、且**直连桩一次都没被调用**；另一例验证队列排空路径仍会真正创建圈选窗口，避免"统一入口"变成空转。按钮按标签包含匹配而非全等，因为「🎙 录制区域」的标签会被热键刷新逻辑改写成「🎙 录制区域 (F6)」。

## 副作用

「📐 拖拽圈选」和「🪟 拾取窗口」现在也经过请求队列，点击到覆盖层出现之间最多约 0.5 秒延迟（`_refresh_loop` 每 500ms 排空一次）。`request_region_capture()` 会立刻 toast「📐 请拖拽圈选目标区域」/「🪟 3 秒后拾取鼠标所在窗口」作为反馈；拾取窗口本来就有 3 秒倒计时，这点延迟可忽略。

换来的是互斥检查只有一处实现，四个入口不可能再各自漂移。

另外，「🎙 录制区域」与「📐 拖拽圈选」现在动作完全一致（都是 `drag`），唯一区别是前者多一跳队列。暂时保留它作为 `F6` 在面板上的可见对应物；若嫌重复可以删掉，或改名成「🎙 拖拽圈选 (F6)」以消除"录制区域内的操作"这一误解——真正的录制是 `F7` 那套。
