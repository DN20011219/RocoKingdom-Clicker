## 3. 订正：曲谱**确实**会随发布包分发

写署名时发现 `data/music/README.md` 与 `docs/changelog/2026-09-28.md` 的说法与事实相反。

**事实**：`dist\RocoKingdom_Clicker\data\music\` 里有全部 6 个 `.mid`，`release\RocoKingdom_Clicker.zip` 里也有。

**根因**：`.gitignore` 只约束版本库，约束不了 `_release_copy.ps1`。后者按顶层条目枚举 `data/`，只排除 `clicker.log` 与 `clicker_configs`，其余整目录递归复制 —— `data/music/` 下的 `.mid` 自然一并进包。09-28 的「快速验证步骤 16」断言"发布包里没有任何 `.mid`"，那条是在一台 `data/music/` 为空的机器上跑的，所以当时确实通过了。

**决定**：保留随包分发，改文档并署名（不是改打包脚本排除）。已就地订正：

- `data/music/README.md`：原「随仓库和发布包一起分发会有版权问题 / 这个 README 只是为了让空目录能被保留」改为「不入 Git，但本地打包会把开发机曲谱复制进发布包」。
- `docs/changelog/2026-09-28.md`：「曲谱为什么不入库」一节加 2026-10-03 订正块；步骤 16 那半句用删除线标出作废并说明理由。仓库有就地订正的先例（09-28 自己就订正过 09-27 的步骤 7）。

**一个连带差异必须记下来**：CI 构建的包**不含** `.mid`。GitHub Actions 从干净的仓库检出，曲谱不入 Git 所以根本不在检出内容里，`data/music/` 只有 README。也就是说 GitHub Release 上的 zip 与本机 `build_release.bat` 产出的 zip 内容不一致。这一点已写进 `data/music/README.md`、`docs/releases/v1.7.md` 的 CI 小节与升级注意事项。

## 5. 区域连点：运行时常驻边框

第四栏「运行控制」新增 `🔲 运行时显示区域边框` 开关（默认打开）。勾选后连点期间区域四周常驻一圈青色边框，用来确认鼠标确实落在预期范围内 —— 此前区域一旦圈定、遮罩消失，就只剩 X/Y/宽/高 四个数字，运行时完全看不到框在哪。

### 难点不是画框，是穿透

区域连点靠 Interception 注入相对位移，注入的点击会落到**光标下最上层的窗口**。一个普通的 topmost 覆盖层会把区域内的点击全部吃掉，功能直接失效 —— 不是"稍微挡一下"，是完全点不到游戏。所以覆盖层必须点击穿透。三层保障按可靠性递减（完整理由记在 `RegionOutline` 的 docstring 里）：

1. **边框画在区域外侧**。`outline_geometry()` 把窗口做成区域每边外扩 `border + margin` = 4px；Tk 的线宽居中于路径，`_draw()` 把路径取在 `pad - border/2`，于是线带覆盖 `[2,4]` 而区域从 `4` 开始，只相邻不重叠。这一层不依赖任何分层窗口或 Win32 支持，是兜底。
2. **Tk `-transparentcolor`**：颜色键 `#ff00fe` 的像素完全透明且不参与命中测试，窗口内部天然穿透。
3. **`WS_EX_LAYERED | WS_EX_TRANSPARENT`**：让边框线本身也穿透。

**失败安全**：第 2、3 层都拿不到时（窗口会整个吃掉点击），构造函数销毁窗口并抛 `RegionOutlineUnavailable`，`_sync_region_outline()` 据此跳过显示并 toast 一次。宁可什么都不显示，也绝不放一个会吞点击的窗口上去。

### 实现要点

- **`RegionSelector.py`**：新增 `outline_geometry()`（纯计算，可脱离 Tk 单测）、`RegionOutline`、`RegionOutlineUnavailable`、常量 `OUTLINE_BORDER` / `OUTLINE_MARGIN` / `OUTLINE_COLORKEY`。
- **另开 `ctypes.WinDLL("user32")` 实例**设 argtypes：`ctypes.windll.user32` 是进程内共享对象，在它上面改会波及其它模块（`DriverInstaller.py:257` 已有另开实例的先例）。顺带记一笔：`WindowFromPoint` 的 POINT 是**按值传递**，不设 argtypes ctypes 会传错，验证脚本一开始就踩了这个。
- **拿 HWND 三途径依次尝试**：`wm_frame()` → `GetParent(winfo_id())` → `winfo_id()`。overrideredirect 窗口下 `wm_frame()` 普遍认为会返回 `0x0`，本机实测返回正常值（`0x930c20`），但后两条兜底保留 —— 这是三层保障里最不可靠的一层。
- **后端一行未改**。`get_region_status()` 只返回 `active` / `total_clicks` / `spots_visited`，不含区域矩形，但 GUI 自己有 X/Y/宽/高 输入框，`_current_region()` 现成可用。
- **生命周期挂在已有的 500ms 轮询上**：`_update_region_ui()` 每拍调 `_sync_region_outline()`；区域未变时立刻返回，否则每 500ms 建销一次 Toplevel 会肉眼可见地闪。停止 → `region_click_active` 掉下来 → 销毁，异常路径同样覆盖，不留残窗。运行中途改 X/Y/宽/高 会重建。创建失败时也记下区域，避免每拍重试。
- **开关不落盘**。它是纯显示偏好，塞进 `region_click` 配置要跟着动 `RegionClickAction`（25 个字段）、`DEFAULT_REGION_CLICK`、`_parse_region_click` 的未知字段处理，不值得。代价是每次启动回到默认打开。

### 实测（真机，非桩）

单元测试用记录桩替换了 `RegionOutline`（真建 Toplevel 会往屏幕上画东西，穿透路径又依赖真实 HWND，不适合在测试里跑），所以另跑了一次真机验证，判据是 `WindowFromPoint`：

| 检查 | 结果 |
| --- | --- |
| 区域中心命中的 HWND | 覆盖前 `0x50656` → 覆盖后 `0x50656`，**未变** |
| 边框线上命中 | `0x50656`，不是覆盖层 |
| `wm_frame()` | `0x930c20`（非 0） |
| `GWL_EXSTYLE` | `0x800a8`，含 `WS_EX_LAYERED`(0x80000) + `WS_EX_TRANSPARENT`(0x20) |
| `-transparentcolor` / `-topmost` | `#ff00fe` / `1` |
| Canvas 矩形路径 | `[3.0, 3.0, 405.0, 305.0]`（400×300 区域 + 4px 留白） |
| 销毁 | 无残窗 |

`WindowFromPoint` 前后返回同一个 HWND，就是"注入的点击能打到游戏"的等价证明。验证脚本是一次性的，跑完即删。

### 已知限制

独占全屏（exclusive fullscreen）游戏里覆盖层画不出来，这是 Windows 桌面合成的限制，不是实现问题；无边框窗口化正常。画不出来时不影响连点本身。
